# @gestaltbi/editor

**[Documentation →](https://gestaltbi.github.io/editor/)** &nbsp;·&nbsp;
**[Open the Studio →](https://gestaltbi.github.io/editor/studio/)**

Read a GestaltBI process graph as a graph: typed nodes, laid out, validated, and
written back without losing what it did not understand.

Renders nothing, like [`@gestaltbi/stream`](https://github.com/GestaltBI/stream),
[`@gestaltbi/storybook`](https://github.com/GestaltBI/storybook) and
[`@gestaltbi/inference`](https://github.com/GestaltBI/inference). It computes the
picture; the host draws it — as SVG for a read-only view, or on a node canvas for
an editable one.

## Install

```sh
npm install @gestaltbi/editor
```

## The shape of it

```ts
import { readGraph, writeGraph } from '@gestaltbi/editor';

const graph = readGraph(processingJson);

graph.nodes     // placed at { depth, lane }, with a kind, a summary and an arity
graph.edges     // { from, to, socket }
graph.problems  // cycles, bad arity, requires that name nothing
```

Every node arrives with somewhere to be, so a host renders without solving
layout:

```ts
for (const node of graph.nodes) {
  draw(node.id, { x: node.depth * 240, y: node.lane * 120 });
}
```

## Positions are derived, never stored

Depth is the longest path from the raw frame, so a node always sits to the right
of everything it reads. Lanes are ordered by the average position of each node's
inputs, which keeps edges short without a full crossing-minimisation pass.

The point is that a `processing.json` written by hand, or generated by a build
script, opens as a readable picture straight away. Nothing has to be migrated to
gain coordinates, and two people editing the same config never produce a diff
that is only about where the boxes moved.

Layout is deterministic: the same config always lays out the same way.

## Nodes say what they are for

The op key tells you which class runs. `kind` tells you what it does to the
data, which is what somebody reading a pipeline for the first time actually
needs:

| kind | ops |
|---|---|
| `prepare` | `format`, `clear` |
| `narrow` | `globalfilter`, `localfilter` |
| `derive` | `enhance`, `diffcalc`, `recognize` |
| `summarise` | `aggregate`, `pivot`, `cohort` |
| `combine` | `join`, `union` |
| `relate` | `correlate` |
| `place` | `geocode`, `geojsonify` |
| `check` | `assert` |
| `settings` | entries that carry options rather than running |

`inputs` carries the op's arity, so a canvas knows how many sockets to draw and
a validator can catch a graph wired more ways than the op reads. Hosts with
their own ops pass their own arities:

```ts
readGraph(config, { arity: { myop: 2 } });
```

## A third of a config is not a stage

Entries named `conf_*` declare `"op": "noop"`, which is not a registered op. They
never run; they exist so views can read their options. Across the three shipped
bundles that is 18 of 51 entries, 11 of 29, and 5 of 18.

They are left off the canvas by default, because a node that cannot run is noise
among nodes that do — and put back untouched when the graph is written. Ask for
them with `includeSettings` if you want to show them somewhere else.

## Problems are reported, not thrown

A config with a cycle in it is exactly the config somebody needs to look at.
Refusing to draw it hands them a stack trace instead of a picture of their
mistake, so `readGraph` always returns a graph and lists what is wrong with it:

```ts
graph.problems
// [{ severity: 'error', code: 'cycle', node: 'a', message: '"a" is part of a cycle: a -> b -> a' }]
```

`cycle`, `missing-require`, `too-many-inputs` and `unknown-op` — the last a
warning rather than an error, since a host may have registered an op this
package has never heard of.

## Round-tripping an existing config

An editor that quietly drops what it did not understand is one nobody can safely
open a real config with. `writeGraph` carries through the top-level keys, every
option exactly as read, the settings carriers that were never on the canvas, and
the original key order — so a diff shows what you changed and nothing else.

There are tests for this. They round-trip all three shipped bundles and assert
the output is byte-identical to the input.

## The Studio

The node canvas this package exists for lives in
[`studio/`](studio) and is published at
[gestaltbi.github.io/editor/studio](https://gestaltbi.github.io/editor/studio/).

Open a config repo by its `org/repo` slug, or a `processing.json` from disk, and
the graph draws itself. Add stages from a palette grouped by what they do to the
data, wire them by dragging between sockets, rename and edit options in the
inspector, and copy the result back out. Problems are listed as you work, and
clicking one selects the stage it is about.

It is Angular with [Rete](https://retejs.org), and it is a *host* — every
decision about what the graph means comes from this package, so the editor and
the read-only view in the product cannot disagree.

Two things it does deliberately:

- **Settings carriers stay on the canvas**, in their own row below the pipeline.
  The read-only view hides them because they are not stages; the editor shows
  them because hiding them would make them uneditable.
- **The document is the source.** Every edit rewrites the config and the canvas
  redraws from it, so there is no moment where the picture and the file disagree.

```sh
cd studio
npm install     # installs the library from .. via its prepare step
npm start
```
